# Working on nautavo

This file is the single source of agent instructions. `CLAUDE.md` only imports it for Claude Code and adds tool-specific notes; keep project instructions here.

## Purpose and scope

nautavo is a static route planner with GPX import/export, built with HTML, strict TypeScript, Vite and MapLibre GL JS. It runs in the browser. It is published as Cloudflare Workers static assets at `https://nautavo.com/` with a `/` base, pages without their extension (`/help`, `/changelog`), in three environments: preview (this maintainer's server, `preview.nautavo.com`, the working tree as it is built), dev (`dev.nautavo.com`, every commit to `main`) and prod (`nautavo.com`, each published release); only prod is indexed. The project was called route-gpx (on GitHub Pages at `route-gpx.t00ls.dev`, retired without a redirect) until 2026-11 (the repository, then `t00ls-dev/route-gpx`, is now `t00ls-dev/nautavo`, and GitHub redirects the old address); stored identifiers keep the old name on purpose: the `route-gpx` IndexedDB database, the `route-gpx-library` backup format, the `route-gpx-last-search` key, the `route-gpx-nominatim` lock and the `route-gpx-shell-` cache prefix. The only server code is the Worker in `src/worker.ts`, which answers the approximate region at `/api/region` (`src/region.ts`) and stores nothing; there is no account system, analytics or remote AI. A Worker function is added only to replace an external service or with an explicit architecture decision, never to store locations. Keep changes compatible with this architecture unless the task explicitly changes it.

Present the project as a route planner with GPX export. Keep public introductions, SEO and sharing assets neutral about transport mode and languages. Language support belongs in the interface selector and the README feature list; do not promote it as a project tagline. Preserve accurate technical explanations of the routing services and their current driving profile where they explain behavior or configuration.

Route creation uses addresses, coordinates and map points. The route-description interpreter has been removed; keep this direct editing flow simple.

## Contracts to preserve

- `Coord` is `[latitude, longitude]`. OSRM URLs and GeoJSON use longitude first; convert at the adapter boundary. Preserve every full-resolution track point and separate GPX track segments. Escape user-provided XML text.
- Server URLs live in two places by design: OSRM, Valhalla and Nominatim are part of `State` (links when non-default, JSON editor, saved routes, backups); Photon and Open-Meteo are device preferences in localStorage (`photon-url`, `weather-server`) and never enter links, saved routes or backups; the approximate region comes from the site's own `/api/region` (the former `region-url` preference was removed in 2026-11 and a stored value is never read). Every Web Storage key is declared in `src/preferences.ts` and read or written only through it; none enters links, saved routes, backups, the JSON editor or requests. Besides the servers, localStorage keeps `language`, `average-speed`, `distance-units`, `temperature-units`, `auto-departure`, `detect-region`, `map-layer`, `satellite-vintage`, `route-coloring`, `route-arrows`, `weather-markers`, `navigation-notice`, `auto-reroute`, `navigation-voice`, `point-placement`, `last-view` (the planner map's center and zoom when the page was last left, read only at startup when the browser cannot tell whether location is allowed) and `route-gpx-last-search` (the time of the last Nominatim search, to space searches across tabs); sessionStorage keeps `panel-open`, `panel-size`, `region-attempted` and `navigation` (while navigating: the planned route's geometry, the address hash it started on and the distance travelled along it, never a position, so a reload continues the same route offline; cleared on End, arrival, Not now and after 30 minutes, `src/navigation-resume.ts`). Key names are stored data: renaming one needs a migration. Moving a server between the two changes the state/link format and needs compatibility handling.
- Servers carried by a link are never used without an explicit choice: a link with non-default routing/search servers opens with the defaults and a notice offers Use link servers. Settings, the JSON editor, saved routes and backups remain explicit user flows.
- Router responses are untrusted: the OSRM and Valhalla adapters build routes through `validRoute` (also used for backups) and reject malformed geometry or values, letting OSRM failures fall back to Valhalla.
- Route steps may carry optional maneuver details: `kind` in OSRM's maneuver-type vocabulary, `modifier` from `MODIFIERS`, a roundabout `exit` (integer 1–20) and the maneuver location `at` as `[lat, lon]`. Both adapters map to this shared vocabulary (Valhalla through `VALHALLA_TYPES`) and omit values outside it; `validRoute` rejects malformed ones in saved routes and backups. The fields stay optional so older saved routes and `route-gpx-library` v1 backups remain valid and reopen without rerouting.
- Imported GPX, TCX and FIT tracks are followed on the road actually taken (#173). After an import, the track is checked once against the roads by Valhalla map matching (`/trace_route`, `map_snap`, `checkTrack` in `src/track-check.ts`, comparison in `src/track-match.ts`). Each piece whose matched road passes `alignedPiece` is replaced by that road as a whole, never stitched with the recording: continuous (parts joined within 30 m), within 3% of the length ridden, through every route point and covering the recording every 100 m within 60 m, except its GPS glitches and the off-road start or end of the route (at most 300 m, the GPS line from indoors), where the route's first and last points move onto the street. Other pieces keep the recording, where GPS glitches the matched road explains (a spike, a zigzag while stopped, a straight jump across a signal gap; `MATCH_THRESHOLDS`), never on a stretch passing a waypoint of the file or at the start or end of the recording, are replaced by that road (across a signal gap only when it is at most twice as long plus 100 m); the comparison follows the track in order and, where the road passes a place twice (out-and-back), takes the pass ahead, so a spur is never cut, automatic stops are placed again on the corrected track, and Keep the recorded track (or undo) restores the recording; stretches no road explains stay as recorded and are flagged on the map and in the summary. Calculate route on an imported track matches its recording again (the pieces are cached) with the same result and takes the directions of the aligned pieces; it never routes the controls or puts another road in place of the track. Reverse and Round trip reuse the geometry with no request, and a point edit reroutes only `EDIT_WINDOW` (1 km) of track on each side of the edited point (`src/track-legs.ts`). Without a connection the check waits for one `online` event; when it cannot run, the import stands unchanged. FIT and TCX import reads only geometry, names, course points and recorded elevation, locally; sensor data is ignored and never stored, and export stays GPX only. A share link stores controls/options, not that geometry, and recalculates when opened. Do not imply that links preserve imported tracks.
- `State` uses version 1. Links are written as `#v2=` (base64url raw DEFLATE via fflate of a positional array, coordinates rounded to 6 decimals, default servers omitted) and `#v1=` links (base64url JSON) remain readable. Keep existing links and the advanced JSON editor compatible; validate links, editor JSON and backups with `validateState` rather than trusting parsed JSON. Legacy speed and `units` values in links, editor JSON and backups are ignored without discarding valid route points.
- Editing a route invalidates the current result and disables stale downloads. Preserve revision checks and discard superseded work so late routing/search responses cannot overwrite newer input or another point's results.
- Language, units and GPX coordinates are independent. Units are device preferences chosen in Settings (`src/unit-preferences.ts`): distance (km/mi: distances, speeds, wind, altitude) and temperature (°C/°F, with weather precipitation in mm/in), each Automatic by default, inferred locally from the device's time zone and, when it names no place (UTC, `Etc/*`), the browser's language region, never from a request (a language region often names only a variety of the language, such as `en-GB` in Australia). Links, saved routes and backups do not carry units (the `#v2=` units slot is kept as 0). Weather requests and risk thresholds stay metric; unit changes only reformat and must not reroute, refetch or alter geometry. Time, arrival, weather passage times and daylight all use the traveler's average speed, never the router duration; while navigating, the arrival and the weather ahead move to the trip's own average with stops (`src/navigation-speed.ts`, blended in over the first 10 minutes), and a badge shows the current speed (#32, #136), measured on the device only. That speed is a device preference in localStorage (`average-speed`, default 20 km/h, or 13 mph where miles are the units) changed only by the user (slider, or the unit switch converting it; `speedNotches` in `src/travel-time.ts`: km/h 1–40 by 1, then by 5 to 80 and by 10 to 120; mph 1–25 by 1, then by 5 to 75; a stored value above the top becomes the top); links, saved routes and backups do not carry it, and legacy values in them are ignored (the `#v2=` speed slot is kept as 0).
- Undo retains up to 50 snapshots in memory, each holding a reference to the route shown for it, so undo restores that exact geometry without rerouting; there is no separate route cache for undo. Preserve point move/removal/reordering behavior and the keyboard shortcut's exclusion of text inputs.
- Routes are saved only by an explicit named save. IndexedDB entries use normalized names for updates; reopening/downloading stored geometry must not request a new route. The one request allowed for a stored route is the step-only refresh when the Itinerary of a route saved before maneuver details existed is opened (`src/directions.ts`): its steps replace the old ones only when the fresh route follows the saved geometry (`sameRoad`), and `updateSavedSteps` stores only the steps, keeping geometry, name and dates; when the road changed, `markDirectionsChecked` records it in the entry (optional `directionsChecked`) so it is not asked again. Storage failure must leave ordinary GPX download usable.
- Favorite places (#52) are an explicit location storage flow: a name, a coordinate, an optional address (up to 240 characters) and a kind (home, work or place, for its icon and order) the user saves from a point's field menu or with Add favorite in Favorite places (Save as favorite, in the app's own sheet in `src/favorite-dialog.ts`, never the browser's prompt), kept in the `favorites` store of the `route-gpx` IndexedDB database (version 2, whose upgrade keeps `routes`), listed in Favorite places right below Saved routes (a tap on a name shows it on the map; editing changes name, icon or place through the same search as a point's field: suggestions, Enter for an address search, pasted coordinates or My location) and offered in every point's field menu, in their own section below the field's commands, with address and distance, filtered by the typed name, where choosing one sets the point with no request; a point already at a favorite (within 30 m) is not offered to be saved again. They never enter links, requests, the JSON editor or metadata; a favorite placed in a route becomes an ordinary route point. Storage failure leaves routing, search and GPX download usable.
- Backups use the `route-gpx-library` format, version 2 (`routes` and `favorites`); version 1 backups (routes only) stay importable. Export backup and Import backup live in Settings (Backup), not in Saved routes. Validate the complete import before writing and keep existing entries with matching names. Do not silently discard saved data or change persistence formats without handling compatibility.
- “Prefer main roads” is a preference, not a guarantee: it routes with Valhalla favoring highways (OSRM if Valhalla fails) and flags the remaining local sections for review. Keep provider road references factual; do not invent classifications.

## Network behavior and privacy

Use every external service within its published terms: rate limits, no heavy or bulk use, a valid User-Agent and Referer (the browser's own) and the required attribution. `docs/SERVICES.md` records each policy with the date it was checked; recheck it when changing how a service is used, and state the worst-case request rate of any new automatic request pattern against those terms. Use the adapters in `src/routing.ts` and `src/search.ts` for routing and search, and `request` in `src/http.ts` for every external request. After an import, the imported track goes to the configured Valhalla server's `/trace_route` once (the pieces of `attributePlan`, also cut at the track's U-turns, `turnarounds`, which a matcher folds away: at most 190 km and about 4,000 points each, at most 10 pieces, by POST, on the serialized routing queue, HTTP 429 stops the rest, page-memory cache of 100 pieces for 15 minutes) with the car profile; a piece whose sent points lie within 60 m of the car profile's answer for less than 90% (roads closed to cars; points weigh time, so a long GPS glitch counts little) is asked once more with the bicycle profile, a fallback and not a retry, and a piece still uncovered is left unchecked (kept as recorded, never flagged). Calculate route on an imported track asks the same pieces again (cache hits ask nothing); worst case 20 requests per import or Calculate, at least 1.5 s apart. Every result passes `safeResult` (every route point and every 100 m of the recording within 60 m of it, except replaced glitches and the off-road start or end, no more than 2% plus 200 m longer) or is discarded and the recording kept. Imported tracks get turn directions only when the Itinerary is opened, through OSRM map matching (`osrmMatch`): points evenly spaced within each leg (restarting at every route point, spacing ladder from 300 m, about 40 requests), requests of at most 10 points (the public server's limit) that never cross a route point, on the routing queue, without retries, with a page-memory cache of 400 requests for 15 minutes so an edit re-requests only the changed legs; the imported geometry never changes. The router order follows Prefer main roads (`calculate` in `src/routing.ts`): with it on (the default), Valhalla is primary with `use_highways: 1`, since the public OSRM cannot favor main roads, and OSRM is the delayed fallback; with it off, OSRM is primary and Valhalla the fallback. Navigation rerouting always asks OSRM first, and a saved route's step refresh asks first the router that made it. Preserve serialized routing starts at least 1.5 seconds apart, the 900 ms route-change debounce, and suppression of stale queued calculations. Do not introduce retry loops. Without a connection (`navigator.onLine` false), Calculate route keeps the route on screen and sends nothing, and a calculation that fails offline says the route will be calculated when the connection returns, then makes one new attempt on the browser's `online` event if nothing changed meanwhile; this single attempt is not a retry loop. The one exception is the Open-Meteo usage limit (the shared per-page budget of 599 coordinates a minute, 4,999 an hour, 9,999 a day and 299,999 in 31 days, or HTTP 429): weather and elevation show a live countdown (`countdown`, "Try again in 30s.") with no retry button, then retry once on their own; refused again, they count down once more and only then show the button. Use Retry-After when the response exposes it, otherwise wait 60 s.

Nominatim searches are explicitly triggered with Enter, not autocomplete. Photon suggests places while typing; do not restore the removed search buttons. Preserve the 500 ms UI debounce, 1.1-second search spacing, in-memory query cache and cross-tab coordination through Web Locks/timestamp storage where available. The timestamp is not a location store. Client-side limits do not enforce aggregate traffic limits across devices.

Keep fetch credentials omitted and service URL validation intact. Retain visible OpenStreetMap attribution. Do not add tile prefetching, bulk downloads or offline tile caching. ## Guided navigation (#31)

Guided navigation follows these rules, agreed in #30; the issues that implement them update the README, help, privacy disclosures and `docs/SERVICES.md` when they ship. The first part has shipped: Navigate in the phone action bar opens a full-screen view (`src/navigation-ui.ts`) that follows the route with the next maneuver, the one after it, the remaining distance and time and the arrival, on a heading-up map. The map follows the direction of travel while moving and the device compass when stopped (`isMoving` hysteresis in `src/navigation.ts`), since mounts and car metal make the compass unreliable in motion; orientation readings stay on the device like positions, and the magnetic heading is turned to true north with the local WMM2025 declination (`src/declination.ts`, public-domain coefficients checked against NOAA's test values; replace them with WMM2030 when it is published). The traveler can zoom (pinch and MapLibre's double-tap-and-drag zoom, both around the map center, and a double tap handled in `src/navigation-ui.ts` that also zooms around the center, so following keeps the traveler in place), pan with one finger and turn the map with two (past MapLibre's rotation threshold, so a pinch only zooms); following keeps a chosen zoom, while a pan or turn leaves a free view that the compass no longer turns. Any view other than following heading-up at the default zoom shows Re-center at the bottom left; the compass button, shown only on a turned map, puts north up (and following then stays north-up until Re-center). The browser's callout, loupe and selection are blocked on this screen (touches on the map cancelled, selection off on the whole page while navigating), since iOS ignores `-webkit-touch-callout` on the map itself. The navigation map (#140) is MapLibre GL JS with OpenFreeMap vector tiles (`liberty` style adjusted in `src/navigation-style.ts`: local `name` labels, streets and roads twice as wide with names sized to stay inside them), the same library, style source and on-demand loader (`src/maplibre-loader.ts`) as the planner's base map (`src/basemap.ts`); it turns with its native bearing, so labels stay upright, and its credits use the planner's modal (`creditsDialog` in `src/map-credits.ts`). Without WebGL the screen shows a notice and the directions only. Return to route, rerouting and voice have shipped (see their rules below). Weather stays in the planner, where it is current: the weather chip the navigation screen once showed (#155) was removed, since a forecast fetched at planning may be hours old, or stale offline, on the way. The sunset or sunrise ahead (`sunAhead` in `src/daylight.ts`, the moments of the planner's summary) shows as a chip ("Sunset in 40 min") when it comes before the arrival and within the hour, computed on the device from the route, the progress and the trip's speed: no request and nothing stored.

- Continuous location: `watchPosition` starts only after an explicit Start navigation (or, on the planner map, `src/user-location.ts`: with the page when the browser already reports the location permission as granted, otherwise after an explicit tap on Use my location; it has no off switch, pauses while the page is hidden and during navigation, stops when the permission is revoked and never changes the route; while the permission is not granted, startup never calls geolocation), shows a visible indicator while active and stops on End, when the page is hidden and when navigation ends. Positions stay in page memory only: they never enter links, saved routes, backups, the JSON editor, storage or requests, except the reroute request below.
- Continue after a reload (#138): a reload during navigation (a discarded tab, a pull-to-refresh) shows the route kept in this tab's `navigation` sessionStorage entry as it was, without routing, and asks Continue navigation or Not now; location and compass start only after Continue, which resumes from the distance travelled so loops and out-and-backs keep their pass. A different address hash, malformed data or an entry older than 30 minutes is discarded.
- Return to route is local first (shipped): `createOffRouteDetector` in `src/navigation.ts` marks the traveler off the route beyond the larger of 50 m and 1.5 × the fix accuracy for 5 s, back within the larger of 25 m and the accuracy, ignoring fixes worse than 100 m; `rejoinPoint` in `src/track-position.ts` picks the point ahead (10 km window) that minimizes 1.4 × the straight line plus the route left; the banner turns amber with an arrow, the straight distance and "Straight line, not by road", the map draws a dashed line and steps out to show the point. Built on `src/track-position.ts` (progress, off-route distance, pass choice by progress), it shows the direction and distance to a rejoin point ahead on the track, never behind the current progress, labeled as a straight-line hint that does not know the roads. It needs no request and works offline. Off-route detection is accuracy-aware with hysteresis and tolerates intentional deviations, since the traveler may use any mode while routes use the driving profile.
- Rerouting (shipped) is online only and within the routing servers' terms (the public OSRM and FOSSGIS servers allow at most one request per second and no heavy use). It leads back to the planned route, not to a new route to the destination: one request from the position to a point 300 m past the rejoin point (never past the next route point), and navigation then follows, in page memory only, the recalculated path joined to the rest of the planned track (`spliceRoute` in `src/navigation.ts`); the planned route, links, saved routes and GPX never change. `createRerouteSchedule` makes it automatic, while the `auto-reroute` device preference is on (the default; the start notice, Settings and, when the notice is hidden, a chip at start say so and turn it off, so a traveler on a fixed course can follow it exactly), only when the device is online and the traveler has been off the route for 15 s, at most once every 60 s and 20 times per navigation, through `navigationRoute` on the existing serialized routing queue (starts at least 1.5 s apart, OSRM then the delayed Valhalla fallback) and without retries: a failure keeps the local hint and says so until the next interval. The Recalculate route button uses the same queue and the 60 s interval and is hidden offline. The request carries the current position at full precision (`gpsPoint` in `src/location.ts`, the 6 decimals of links, chosen by the maintainer so the route starts on the right street) and, while moving, the GPS course as OSRM `bearings` / Valhalla `heading` (±60°); that position is the only one ever sent, at that moment only, and is never stored. Worst case: one routing request a minute per device, plus the fallback on an OSRM failure.
- Without tiles or the map style, the route line, maneuvers and position still draw over a neutral background with a notice; navigation never depends on tiles. The tile rules above stay: no prefetching, no bulk downloads and no offline tile caching, which the OpenStreetMap tile policy forbids.
- Screen and voice: request a Screen Wake Lock while navigating and release it on stop, and say that browsers stop tracking with the screen off or the tab hidden. The start notice says it without naming a browser; the help and README add that iOS Safari is the strictest. Voice announcements (#190, shipped) use the local `speechSynthesis` only, off by default (the `navigation-voice` device preference, switched in the start notice, Settings and a speaker button on the navigation screen); no remote speech service. `src/navigation-voice.ts` decides what to say: the next maneuver far, near and at the turn (`VOICE_THRESHOLDS`, growing with speed), arrival, leaving and rejoining the route, a recalculated route and the sunset ahead (`VOICE_SUNSET_MINUTES` before it, or at once when less remains, after any maneuver), each once, as English source text that `src/i18n.ts` translates for speech (abbreviations in full); speech starts from the Start or Continue tap (iOS needs one) and stops on End and while the page is hidden. - Safety: a large-text navigation view with few controls. A notice when navigation starts gives only safe-use recommendations (avoid handling the phone while moving, use a mount in view, check the route before leaving; keep the tab open and the screen on), with a Don't show this notice again checkbox stored as the `navigation-notice` device preference and turned back on in Settings; it does not block use, because the traveler needs the screen to find the way and a passenger may be the one using it.
- Service worker (`src/sw.ts`, #126): it caches the same-origin build files of one build only (the app, help and What's new, their hashed assets, icons, manifest and notices, listed by `precacheList` and versioned by a hash of their contents in `vite.config.ts`; pages are fetched and cached under their public URLs `/`, `/help` and `/changelog` (`precacheUrl`), never their `.html` addresses, which Cloudflare redirects and a navigation would refuse from the cache), so a saved route opens and can be followed without network. Pages are network-first with a 4 s fallback to the cached page, fetched with `cache: 'no-cache'` (a page a browser or proxy kept from before a deploy names assets that are gone), and a fresh page is never stored, so a page and its assets always come from the same build; registration uses `updateViaCache: 'none'` and a new build replaces the old cache on activation. A home-screen web app is resumed rather than reloaded, so `keepUpdated` in `src/offline.ts` asks for a new service worker each time the page is shown again and, once a new build takes over, reloads the page: at once if it was not touched since it was shown, otherwise the next time it is shown, never during guided navigation (the route reopens from the address). It never intercepts or caches cross-origin requests (tiles, routing, search, weather, elevation, road attributes), and same-origin requests outside its file list, such as `/api/region`, go to the network; route data stays in the existing IndexedDB library. A new deploy must activate predictably, never leaving an outdated app in use, and the manifest keeps `display: browser` with no install prompt (Add to home screen only explains the browser's steps).

Create a focused branch named `<type>/<short-description>` (for example `fix/gpx-import-names`), push it, open the PR with `gh pr create` following `.github/pull_request_template.md`, watch its CI run and merge with `gh pr merge --squash --delete-branch` only when the merge is authorized. The PR title becomes the squash commit title, so write it in the history's concise imperative English style. Dependabot PRs follow it too: before merging, retitle them from `Build(deps): Bump …` to the same style (for example `Update MapLibre GL JS, Prettier, typescript-eslint and Vite`).

The required check is the CI gate job `Lint, test and build`, which depends on the static-check job and every browser shard. Renaming that job breaks the required check; such a change must update the ruleset in the same authorized task. Changing, disabling or bypassing rulesets, merge settings or security features (Dependabot alerts and security updates, private vulnerability reporting) is a separate repository-administration task that needs its own authorization.

## Hosting and publication

Cloudflare Workers serves `dist/` as static assets (`wrangler.jsonc`) and runs `src/worker.ts` for `/api/*` (`run_worker_first`) and for paths no file matches (its 404, with `no-store` and `noindex`, since `_headers` does not reach Worker responses), in two Wrangler environments named like the GitHub environments: `prod` (Worker `nautavo-prod`, `nautavo.com`) and `dev` (Worker `nautavo-dev`, `dev.nautavo.com`); the top level is only for `wrangler dev` and is never published under a domain. `workers_dev` and preview URLs are off so each environment has one public address, and observability is off so no request is logged. `html_handling: auto-trailing-slash` publishes each page without its extension (`/help` serves `help.html`; `/help.html` and `/help/` redirect to `/help`), so links, canonicals, the sitemap and the manifest use `/help` and `/changelog`, and `pageKey` in `src/precache.ts` maps them to the cached files. `public/_headers` makes `/assets/*` immutable for a year (every name there carries a content hash); everything else keeps Cloudflare's default of revalidating every request, and each page in the sitemap adds `no-transform` to it, so Cloudflare never rewrites the HTML (its Web Analytics beacon was injected on nautavo.com through a zone setting the dashboard hid; a test checks one rule per sitemap page). Security headers come from `src/security-headers.ts` (a strict Content-Security-Policy, HSTS without preload, `nosniff`, `X-Frame-Options: DENY`, the browser's default Referrer-Policy stated, since the services' terms rely on the Referer, and COOP): the build adds them for every path to the published `_headers`, the Worker sends them with its own answers, and the dev server and preview send them too (dev also allows the `<style>` elements Vite injects and http services on the local machine, which the published policy refuses so the site connects only to https), so the browser suite runs under the published policy. Anything new the app loads (a service host is already covered by `https:`, but a new worker, frame, font or inline code) must fit that policy or change it there, never with `unsafe-inline` or `unsafe-eval` in `script-src`. Changing the domain, DNS, certificates or the Worker's settings in the Cloudflare dashboard is a separate authorized infrastructure task. Self-hosted copies build with `SITE_URL` set to their own host root (`src/site.ts`); the site's own builds leave it unset. Preserve Vite's `/` base and the app, help and What's new (`changelog.html`) build entries. A hosting-path change also requires reviewing manifest `id`/`start_url`/`scope`, canonical/social URLs, sitemap and docs.

Three workflows handle checks, publication and monitoring. Every job sets `timeout-minutes` to about four to five times its usual duration (checks 10, each browser shard 15, report merge and gate 5, Deploy 15, Lighthouse 30), so a stuck job stops in minutes rather than GitHub's 6-hour default; raise a limit when a job's normal duration grows. `.github/workflows/ci.yml` (CI) runs the static checks (lint, format and unused code), unit tests and build in one job and the browser suite in 8 shards, merges their reports and reports the result through the `Lint, test and build` gate job for pull requests, main pushes and manual dispatch with only `contents: read`, in the non-cancelling `ci-<ref>` concurrency group. `.github/workflows/deploy.yml` (Deploy) publishes to dev after a CI run triggered by a push to `main` succeeds (rebuilding that run's exact `head_sha`, with `X-Robots-Tag: noindex` added to `dist/_headers`) and to prod when a release is published (rebuilding the release commit, only if CI passed on it as a push to `main`; prereleases are skipped), with `npm run deploy` and `CLOUDFLARE_ENV` set to the target. The GitHub environments `dev` (branch `main` only) and `prod` (tags `v*` only) each hold the Cloudflare token (a user API token limited to the account's Workers and the nautavo.com zone) and account ID, passed only to the publishing step; values are set by the maintainer in a private terminal (`gh secret set NAME --env dev|prod`), never through chat or the repository. Preserve Deploy's `contents: read`, its non-cancelling `deploy-<environment>` concurrency groups, dev's current-main guard (an older commit cannot publish over a newer one) and prod's CI check. The local preview sends `X-Robots-Tag: noindex` too (`preview.headers` in `vite.config.ts`). `workersParity` in `vite.config.ts` keeps the local servers like Workers where the app depends on it: dev and preview answer `/api/region` with the Worker's own code (204 without a Cloudflare location), and the preview redirects `.html` page addresses to their public URL, so `offline.spec.ts` meets the same redirects as the published site. Every checkout uses `persist-credentials: false`. `.github/workflows/lighthouse.yml` (Lighthouse) runs `npm run lighthouse` against the live site with three runs per page on Dependabot's schedule (Monday 09:17 UTC, the same cron expression `17 9 * * 1` as both Dependabot updates) and on manual dispatch, with only `contents: read` in the non-cancelling `lighthouse` concurrency group; it posts the score table to the run summary and the reports as an artifact, is not a required check and never builds or publishes. A failed audit is a regression to investigate in its own task, not a reason to rerun it. Keep Cloudflare secrets out of CI and do not add a manual trigger to Deploy. Never rerun old workflow executions to publish; watch only the runs belonging to the authorized new commit.

When publication is part of the task, deliver the change through an authorized pull request as described above; the push to `main` comes from its squash merge and publishes dev. Then follow the CI run for the merge commit on `main` and the Deploy run it triggers with `gh run watch <id> --exit-status`, and distinguish successful checks from successful deployment. Prod changes only through a release (CONTRIBUTING.md), which needs its own authorization; follow its Deploy run the same way. Confirm the requested behavior on the live site (dev.nautavo.com or nautavo.com); do not infer it from a green build alone.
